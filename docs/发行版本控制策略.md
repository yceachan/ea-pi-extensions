# ea-pi-extensions 版本控制与发布指南

本仓库按包维护独立版本，以 `<pkg>@<version>` tag 将发布物绑定到源码提交。维护者通过 `gbump` 准备版本、提交和 tag，通过 npm 或发布工作流完成上传，再分别核对代码检查、发布结果与包的可下载状态。独立加载的 Pi 扩展通过宿主服务接口协作；npm 依赖树、Pi 扩展加载与发布授权各自承担明确职责，发版操作应围绕这些边界展开。

> [!note]
> **Ref:** [提交规范](git提交规范.md) | [测试与 CI 指南](test-CI-Guide.md) | [gbump](../scripts/gbump.mjs) | [mono-release](../scripts/mono-release.mjs) | [mono-tagcheck](../scripts/mono-tagcheck.mjs) | [发布工作流](../.github/workflows/publish.yml) | [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) | [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/)

## 包、依赖与版本边界

根 `package.json` 是 `private: true` 的 Bun workspace 容器，各包在 `packages/*/package.json` 中维护自己的 semver。按本项目约定，修复和小幅调整用 patch，重大功能及 0.x 阶段的破坏性变更用 minor，进入稳定主版本时用 major；只有本次实际变更的包推进版本。

### npm 安装与 Pi 加载

| 对象 | manifest 约定 | 安装与运行方式 |
| --- | --- | --- |
| Pi 宿主 SDK 与公共类型 | `peerDependencies` 使用 `"*"`；开发验证所需版本写入 `devDependencies` 并由锁文件固定 | 运行时复用宿主，开发时使用锁定的 SDK |
| 包内部实际导入的第三方运行库 | `dependencies` | 由 npm 安装到该包的依赖树 |
| 由 Pi 独立加载、经宿主接口发现的扩展服务 | 分别在各自 `pi.extensions` 声明入口 | 用户分别 `pi install`，Pi 将它们加载到同一进程 |

`pi-codex-imagegen` 与 `pi-wsl-browser` 通过 `pi.events` 的 `pi-shelld:service:v1` 通道取得 `start/close` 服务。它们的 manifest 保持与 pi-shelld 的 npm 依赖解耦；用户独立安装服务扩展和消费者扩展：

```bash
pi install npm:@yceachan/pi-shelld
pi install npm:@yceachan/pi-codex-imagegen
# 使用浏览器扩展时另行安装
pi install npm:@yceachan/pi-wsl-browser
```

本地开发时显式加载对应目录：

```bash
pi --no-extensions -e packages/pi-shelld -e packages/pi-codex-imagegen
```

包元数据同时维护 `keywords: ["pi-package", ...]`、`pi.extensions` / `pi.skills`、正确的 `repository` 与 `homepage`、发布 `files` 白名单及 `publishConfig.access: public`。调整安装方式时，同步包 README 与锁文件；沿用包已有的双语文档约定。

### 逐包 tag 与 registry 基线

逐包 tag 使用不带 scope 的 `<pkg>@<version>`，例如 `pi-gadget@0.3.0`；npm 名称带 `@yceachan/` scope。`publish.yml` 解析 tag，核对该 tag 下 manifest 的版本，再发布指定包。

regular 发布从该包 registry 中最高的正式 `X.Y.Z` 版本推进。本地 manifest 与该基线一致时，可以使用 patch / minor / major 或更高的显式版本；首次发布使用 initial，保留 manifest 当前版本，fork 包也适用。

Git 批量发布通过 atomic push 保证分支与全部 tag 同进退。npm 按每个 tag 分别发布，各包的上传结果与恢复状态分别核对。

## 使用 gbump 发版

![逐包发布流程](https://ali-oss-yceachan.oss-cn-chengdu.aliyuncs.com/img-bed-typora/package-release-flow.svg)

### 发布准备

在准备发布的干净检出中完成以下工作：

1. 完成代码、包元数据与安装说明；依赖变动后刷新并审查 `bun.lock`。
2. 创建并填写目标版本的 `changelog/<pkg>/vX.Y.Z/log.md`，与代码一并提交。
3. 按[测试与 CI 指南](test-CI-Guide.md#ci-结构)选用与 CI 一致的 Bun，运行安装、类型检查和默认测试。
4. 核对待发布提交、包版本、已有 tag 与 registry 基线，再运行 gbump 干跑。

```bash
./gcm -c -p pi-gadget --minor
# 填写 changelog，暂存本次代码及发布说明后，按 ./gcm --help 提交

bun install --frozen-lockfile
bun run typecheck
bun run test
```

`gbump` 自身负责 clean tree、README 同步、registry 基线、有效 changelog 与 tag 状态守卫；代码验证由上述测试入口和主分支 CI 承担。原工作区含其他任务的未提交改动时，保留原文件，选择已提交源码的干净检出执行发布。

### regular：单包与多包发布

```bash
./gbump -p pi-gadget --patch --dry-run
./gbump -p pi-gadget --patch

./gbump -p pi-gadget --minor -p pi-shelld --patch --dry-run
./gbump -p pi-gadget --minor -p pi-shelld --patch

./gbump -p pi-gadget --set-ver 0.5.0 --dry-run
```

重复 `-p` 开始新的包规格，每包单独指定版本模式。全部预检通过后，脚本修改所选包的 manifest，更新 `bun.lock` 中的 workspace 版本，创建一个 `release: <tag1>, <tag2>, ...` 提交，再为每包创建指向该提交的轻量 tag。当前分支和这些 exact tags 一次 atomic push 到 origin，每个 tag 各自触发 `publish.yml`。

`gbump` 将所有包规格一次委托给 `mono-release.mjs`，守卫与版本写入逻辑共用一份实现。`--dry-run` 走预检并展示计划，正式执行时才写版本、提交和 tag。

### initial：首次发布当前版本

```bash
./gbump -p pi-new --initial --dry-run
./gbump -p pi-new --initial
# 凭据缺失时才使用内置登录分支
./gbump -p pi-new --initial --login
```

initial 每次处理一个包，使用 manifest 当前版本。它核对 registry 与两端 tag、README 和 changelog，执行 npm 身份检查及 tarball 干跑；确认后在 HEAD 创建或复用 local tag，本地执行 public publish，依次推送分支与 exact tag。版本文件保持原值，HEAD 沿用已有源码提交。

当前实现的 initial 及其 dry-run 都会运行 `npm whoami`。已有有效凭据时直接运行上述发布命令，根据 `npm publish` 实际返回的链接完成发布授权；遇到 `ENEEDAUTH` 时再通过 `--login` 获取登录链接。`--dry-run` 保持只读，补齐凭据后可重新走查。

TTY 实发需要输入完整 tag；非 TTY 实发使用 `--yes` 授权执行。浏览器或 OTP 形式的账号验证由 npm 按当前操作发起。initial 使用独占模式，regular 多包批次另行执行。

发布中断后重跑同一 initial 命令，脚本按已发布版本及 HEAD 上的 tag 恢复剩余步骤。恢复期间保持源码提交与版本一致。

## npm 授权与发布恢复

### 根据实际操作完成授权

| 授权 | 触发操作 | 作用域 |
| --- | --- | --- |
| npm 登录 | 凭据缺失时的 `npm login`，或 initial 的 `--login` 分支 | 建立本机 npm 身份 |
| 发布 2FA | 本地 `npm publish` 返回的浏览器链接或 OTP 提示 | 验证本次发布；后续操作是否复用授权窗口由 npm 决定 |
| Trusted Publisher | npm 包设置中的 CI 信任配置 | 授权指定仓库和 workflow 使用 OIDC 发布该包 |

本地发布优先执行发布命令，再响应它实际提出的认证要求。代理应即时转交当前终端进程生成的授权链接，保留该进程等待用户完成验证；链接失效时，重新发起对应操作取得新链接。账号验证在 npm 页面或交互终端完成。

网页授权使用支持该流程的 npm CLI，并在真实终端或 PTY 中运行，保证授权链接完整显示。`--yes` 处理 gbump 的执行确认，npm 继续独立处理账号验证。登录成功、发布获准和 CI 信任配置是三个需要分别检查的状态。

### 为每个包配置 CI 信任

常规自动发布通过 GitHub Actions OIDC 执行。包存在后，在 `https://www.npmjs.com/package/@yceachan/<pkg>/access` 配置 GitHub Actions Trusted Publisher：

| 字段 | 本仓库取值 |
| --- | --- |
| Organization or user | `yceachan` |
| Repository | `ea-pi-extensions` |
| Workflow filename | `publish.yml` |
| Allowed actions | 允许当前工作流使用 `npm publish` |

配置与[实际发布工作流](../.github/workflows/publish.yml)对应后，由 GitHub 的 `id-token: write` 权限提供 OIDC 身份。CI 认证失败时，核对该包设置、仓库、workflow 文件名、允许的操作与 runner；本机登录态单独用于本地操作。字段含义以 [npm 官方文档](https://docs.npmjs.com/trusted-publishers/)为准。

### 从原发布提交补发

维护者选择本地补发时，使用原 tag 对应的干净检出，保留既定包名与版本。先查询目标版本；确认尚未发布且没有已提交但仍在处理中的上传请求后，再执行该版本的 `npm publish`，根据它返回的链接完成 2FA：

```bash
npm view @yceachan/pi-codex-imagegen@0.1.1 version
# 在原发布 tag 的干净检出中补发
npm publish --workspace=@yceachan/pi-codex-imagegen --access public --browser=false
```

npm 接收上传后，等待目标版本进入公开 registry，再重跑原 `publish.yml` run。工作流查询到版本已存在后跳过上传，继续创建该 tag 的 Release 页面。已发布包的来源记录由实际上传操作确定；工作流重跑负责补齐它后续的步骤。

## 验证发布是否完成

| 检查对象 | 完成条件 | 查看入口 |
| --- | --- | --- |
| 代码检查 | 对应源码的安装、类型检查与默认测试通过 | `ci.yml`，通常由 main push 触发 |
| 每包发布工作流 | 每个目标 tag 的 run 成功，包名、版本与源码提交匹配 | `publish.yml` |
| npm 包 | 目标版本可查询，发布 manifest 符合预期，实际 tarball 可下载 | registry 元数据与包下载 |
| Release 页面 | 每个 tag 存在对应发布说明页面 | GitHub Releases |

两个 workflow 各自触发，交付时逐项核对。批量发版的 run 标题可能相同，查看 `headBranch` / tag 与 `headSha` 来区分各包及 main CI。

```bash
gh run list --workflow ci.yml
gh run list --workflow publish.yml
# 查看目标 run 的提交、ref、结果和失败步骤
# gh run view <run-id> --json headSha,headBranch,status,conclusion,jobs

npm view @yceachan/pi-codex-imagegen@0.1.1 version dependencies dist.tarball --json
npm pack @yceachan/pi-codex-imagegen@0.1.1 --pack-destination /tmp

gh release view pi-codex-imagegen@0.1.1
```

npm 提示上传已接收、正在处理时，继续等待公开版本和下载资源可用。版本元数据与 tarball 可能先后出现；在它们均就绪后确认可安装，并按需要重跑发布工作流。

### 按失败位置恢复

| 状态 | 下一步 |
| --- | --- |
| main CI 在 frozen install 失败 | 按[测试指南](test-CI-Guide.md#ci-结构)对齐 Bun 版本，在干净检出复现，再审查 manifest 与锁文件 |
| CI 在 npm 发布阶段报 `ENEEDAUTH` | 核对该包 Trusted Publisher；维护者选择本地补发时，走原 tag 的发布授权流程 |
| npm 已接收上传，公开查询或下载尚未就绪 | 保留既定版本与 tag，等待 registry 和 tarball 可用后复验 |
| npm 版本已存在，Release 页面缺失 | 重跑原发布 run，利用已发布版本跳过机制补齐页面 |
| initial 的 publish / push 中断 | 保持 HEAD 与 tag 一致，重跑同一 initial 命令 |
| regular 的 push 失败 | 核对本地 release commit、目标 tags 和远端 refs，补齐原分支与 exact tags 的 atomic push |
| changelog 缺失或为空 | 创建目标版本说明，填写实质条目并提交，再运行 gbump |
| 本地版本落后于 registry | 使用 version sync 对齐并审查锁文件变更，再准备发布 |
| 本地版本领先 registry，或已有目标 tag | 先核对上传、版本、源码与两端 tag 状态，再选择恢复步骤 |

## 辅助工具

### 版本基线维护

`mono-tagcheck.mjs` 负责版本号检查、同步和复位；Git 提交、tag 与推送由发版流程负责。

```bash
bun run version:check
bun run version:sync --dry-run
bun run version:sync
bun run version:reset --dry-run
```

sync 将落后包对齐到各自 registry 的最高正式版本，随后运行 `bun install` 刷新锁文件；领先包需要先处理未完成的发布。reset 用于确认发布未完成后的版本复位，先审阅 dry-run，再核对全部文件变化。

宿主 SDK 的开发依赖可使用明确版本或静态 semver 范围，配合已提交的锁文件固定测试输入。跟随上游时，更新声明或运行 `bun update`，使用与 CI 一致的 Bun 刷新并验证锁文件；运行时仍遵循前述宿主 peer 依赖约定。

### README 与提交辅助

```bash
./sync-readme --check
./sync-readme --dry
./sync-readme

./gcm --help
./gcm --list
./gcm -c -p pi-gadget --patch
```

`sync-readme` 维护根目录两个 README 的包清单和安装块，包描述沿用既有译文，新增条目取 manifest 描述。gbump 的 README 守卫要求这些清单已同步。

`gcm -c` 按目标版本创建 changelog 骨架。填写后优先随功能改动提交；代码已提交时，单独提交发布说明。`gcm` 与 `gbump` 的 `-p` 共用 scope 解析，支持唯一模糊包名与包内工具到母包的映射；非交互操作使用明确包名更便于审阅。

zsh 补全位于 `scripts/completions/_gbump`，安装时将该目录加入 `fpath`，再运行 `compinit`。完整参数及守卫提示以 `./gcm --help`、`./gbump --help` 为准。
